# 지출결의서 앱 현황 진단 문서 (기능 인벤토리 + 스펙 대조)

- 날짜: 2026-08-31
- 목적: 새 기능 스펙을 쓰기 전에, 지금 `실행.bat`(Flask 앱)이 실제로 무엇을 하는지 코드 기준으로 확정하고, 지금까지 작성된 4개 설계 문서가 실제로 얼마나 구현됐는지 확인한다. wikidocs PRD.md 템플릿의 항목(배경/범위/기능 요구사항/리스크·열린 질문)을 "앞으로 할 일"이 아니라 "지금 상태"에 맞게 변형해서 썼다.

## 1. 배경

- 이 앱은 4개의 설계 문서(spec)를 거치며 성장했지만, `.superpowers/sdd/progress.md`(태스크 실행 추적 로그)는 처음 2개 스펙까지만 기록이 남아있고 이후 것은 추적이 끊겼다.
- 그 결과 "설계 문서에 쓴 것 = 실제로 동작하는 것"이라고 믿을 수 없는 상태였다. 이 문서는 그 간극을 코드를 직접 읽어서 메운 기록이다.

## 2. 현재 구현된 기능 (코드 기준 인벤토리)

`app.py` 라우트 기준:

| 라우트 | 기능 |
|---|---|
| `GET /` | 폼 렌더링 (이력/과제 프리셋 로드) |
| `POST /add_project` | 과제 프리셋 추가 |
| `POST /update_project` | 과제 프리셋 수정 (원래 이름으로 대상 지정) |
| `POST /delete_project` | 과제 프리셋 삭제 |
| `POST /refresh_read_seed` | `read/` 폴더의 과거 지출결의서 xlsx를 스캔해 이력/과제에 병합 |
| `POST /parse_pdf` | 업로드한 견적서 PDF에서 품목/업체명/제목 인식 |
| `POST /generate` | 입력값으로 xlsx 생성·다운로드 + 이력/과제 기록 |

기능적으로 정리하면:

1. **기본 정보 입력** — 업체명/문서번호/발의일/지출일/청구부서/청구인, 자유 입력 + 이력 기반 datalist.
2. **내용(제목)/상세내용 입력** — 이력 기반 datalist, 상세내용은 이전 값 선택 드롭다운.
3. **과제 정보 CRUD** — 과제 선택(프리셋 자동 채움) + 화면에서 직접 추가/수정/삭제, `project_name`을 키로 매칭, 축약 표시명은 저장된 `label`이 있으면 그것을, 없으면 키워드 매칭(`PROJECT_LABEL_KEYWORDS`)으로 자동 생성.
4. **품목 표 입력** — 규격/단위/수량/단가 4개 체크박스로 켜고 끄기 가능(고정 4개, 순서 불변). 단가를 끄면 공급가 직접 입력으로 전환.
5. **PDF 품목 자동 인식** — 업로드/드래그드롭 → 표 추출 → 헤더 동의어 매칭 → 품목/규격/단위/수량/단가 채움. 계층형 대분류 접두어 처리, 중복 단가열 보정, 합계행 제거, 표가 없으면 문단 패턴 fallback.
6. **PDF 업체명 자동 인식** — 라벨 패턴(상호/업체/회사명/발신/공급자) 우선, 없으면 `(주)`/`㈜`/`주식회사` 반복 패턴으로 추정. 자사(그린플러스) 오인식 방지 로직 포함.
7. **PDF 제목 자동 인식** — 라벨(내용/물품명/견적명/제목 등) + 콜론 뒤 값, "~의 건" 접미사 자동 부여. *(주의: 이 기능은 4개 스펙 어디에도 설계 문서화되어 있지 않다 — §5 참고)*
8. **read 폴더 이력 시딩** — 수동 새로고침 버튼으로 `read/` 폴더의 과거 xlsx를 스캔해 이력/과제 프리셋에 중복 없이 병합.
9. **품목 표 동적 컬럼 배치 + 초과 행 처리** — 활성 필드 수에 따라 폭을 재분배하고, 품목이 기본 9개 슬롯을 넘으면 행을 늘리고 결재란/각주 블록을 아래로 밀어냄. *(주의: 초과 행 처리 로직도 스펙 문서화가 안 되어 있다 — §5 참고)*
10. **입력 이력 로컬 저장** — `data/history.json`, `data/projects.json`에 저장, 앱 재시작 후에도 유지.
11. **엑셀 생성/다운로드** — 회사 양식(rev.2) 그대로 채운 `.xlsx` 파일명 자동 생성(`지출결의서_{업체명}_{날짜}.xlsx`).

## 4. `2026-08-05` 스펙 상세 — 무엇이 다르게 구현됐나

이 스펙은 "구현 대기" 상태로 표기돼 있지만, 실제로는 부분적으로(그리고 스펙과 다른 기술적 선택으로) 구현되어 있다. `progress.md`에 이 스펙에 대한 태스크 기록이 전혀 없는 것도 이 혼란의 원인으로 보인다.

| 항목 | 스펙 설계 | 실제 코드 | 판정 |
|---|---|---|---|
| A. PDF 헤더 동의어 확장 (`QUANTITY`, `PRICE` 추가) | `HEADER_SYNONYMS`에 `QUANTITY`/`PRICE` 추가 + `match_field_fuzzy`를 표 헤더 매칭 경로에 연결 | `HEADER_SYNONYMS`에 `QUANTITY`/`PRICE` 없음. `match_field_fuzzy`는 문단 fallback 경로(`extract_paragraph_fallback`)에서만 쓰이고 표 헤더 매칭(`find_header_row`/`map_table_columns`)에는 연결 안 됨 | ❌ 미구현 |
| A. 품목명 칸 좌표 기반 복구 (선 없는 표) | `pdfplumber`의 `find_tables()`+`crop()`으로 빈 품목명 칸 복구 | 코드에 `find_tables`/`.crop(` 호출 전혀 없음 | ❌ 미구현 |
| B. 과제 프리셋에 `short_name` 필드 추가 + 10개로 정리 | JSON에 `short_name` 필드 저장 | `short_name` 필드 없음. 대신 `PROJECT_LABEL_KEYWORDS` 키워드 매칭으로 매번 계산(`short_label()`), 사용자가 명시적으로 지정한 경우만 `label` 필드로 저장 | △ 다른 방식으로 목표 달성 (10개 정리는 됨, 저장 방식만 다름) |
| C. PDF 업체명 자동 인식 | `extract_tables()`로 라벨-값 셀 매칭 우선, 실패 시 문단 콜론 패턴 | `extract_company_name()` 존재, 라인 단위 정규식 라벨 매칭 + `(주)`/`㈜`/`주식회사` 반복 빈도 기반 추정으로 구현 — 표 셀 단위가 아니라 텍스트 라인 단위 | ✅ 목표는 구현됨 (기술적 접근만 다름) |
| D. 과제 프리셋 CRUD, `id`(uuid4) 기반 REST API (`POST/PUT/DELETE /api/projects/<id>`) | 고유 `id` 필드 + REST 라우트 | `id` 필드 없음. `project_name` 문자열을 키로 쓰는 `POST /add_project`, `/update_project`, `/delete_project` (전부 POST) | △ CRUD 자체는 동작하지만 스펙의 API 계약과 다름. `project_name`을 바꾸는 수정 시 `original_name`으로 대상 지정 — 동명 과제가 있으면 취약 |

## 5. 스펙에 없는 기능 (문서화 안 된 채 구현됨)

코드에는 있지만 4개 스펙 어디에도 설계 근거가 없는 기능들:

1. **PDF 제목(내용) 자동 인식** (`extract_title`, `_ensure_case_suffix` 등) — 언제, 왜 추가됐는지 기록이 없음.
2. **품목 초과 시 행 추가 + 결재란/각주 블록 밀어내기** (`_capture_footer_block`/`_restore_footer_block`/`BASE_ITEM_ROWS` 로직) — git log상 커밋은 있으나(`e0d7bfa` 등) 스펙 문서 없이 진행됨.
3. **회사 양식 rev.2 전환** (`eeadc22` 커밋) — 템플릿 자체가 바뀐 큰 변경인데 스펙 없음.
